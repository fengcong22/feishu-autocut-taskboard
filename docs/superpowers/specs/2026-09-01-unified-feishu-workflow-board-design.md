# 当前学科单页统一流程看板设计

## 目的

Taskboard 当前把“已完成剪辑”“上传队列”“上传中”“已经上传”放在多个独立视图中。操作人员需要来回切换页面，难以判断一条任务目前处于哪个环节。

本次设计将当前选中的一个飞书学科表显示为一个统一流程看板，让剪辑和上传状态在同一页面中连续呈现。不同 Base、不同学科的任务仍然完全隔离；切换左侧学科后，只加载并显示该学科的任务。

## 范围与约束

第一阶段只调整 Taskboard 前端展示和交互，不改变：

- Bridge 的事件筛选、去重、重试和任务登记规则；
- Auto-Cut 的启动、并发、五秒延时和 Codex 调用规则；
- ZIP 校验、上传复制、重试和目标路径安全校验；
- 飞书记录回写行为；
- Taskboard 内部稳定的任务状态值和上传状态值。

现有独立视图和后端接口保留兼容性。统一看板成为选中学科的默认工作入口，旧视图不再作为日常流程的主要入口。

## 页面结构

### 左侧导航

左侧继续显示：

1. 多维表格（Base）；
2. 该 Base 下已选择显示的学科子表；
3. 当前选中的学科高亮。

切换学科时，统一看板、搜索、筛选和上传统计全部切换到新的学科范围，不混入其他 Base 或子表任务。

### 顶部上下文

统一看板顶部显示当前上下文：

`Base 名称 / 学科子表名称`

右侧保留搜索、筛选、自动化入口和新建任务入口。学科配置仍从配置入口打开，不把其他 Base 的配置内容塞进当前面板。

### 主看板列

桌面端使用横向可滚动的流程列；每列保持稳定宽度。首版列顺序如下：

1. 待处理（内部状态 `todo`）；
2. 排队中（内部状态 `queued`）；
3. 处理中（内部状态 `in_progress`）；
4. 待验收（内部状态 `in_review`，只对手动模式任务实际出现）；
5. 已完成剪辑（任务已完成且 ZIP 已验证，但尚未进入上传或没有上传记录）；
6. 上传队列（ZIP 状态 `queued`，失败项在该列以失败标记显示）；
7. 上传中（ZIP 状态 `uploading`）；
8. 已上传（ZIP 状态 `uploaded`）。

“失败”首版不单独增加一列，而是在“上传队列”列中使用醒目的失败状态、错误原因和重新上传操作。后续的可配置流程阶段再决定是否把失败独立成列。

### 任务归属规则

一个任务在统一看板中只显示在一个当前阶段，避免同一任务同时出现在“已完成剪辑”和“上传队列”等多个列。归属按以下优先级计算：

1. 只要该任务存在上传中 ZIP，归入“上传中”；
2. 否则只要存在排队或失败 ZIP，归入“上传队列”；
3. 否则任务已完成且存在已验证 ZIP，归入“已完成剪辑”；
4. 否则按任务内部状态映射到“待处理”“排队中”“处理中”或“待验收”；
5. 已取消、已归档和普通非飞书任务沿用现有“其他任务/归档”入口，不进入当前学科流程列。

同一任务存在多个 ZIP 时，列归属使用上述优先级，卡片显示 ZIP 数量和各 ZIP 状态摘要；具体文件、SHA-256、目标路径和重试操作在任务详情中查看。

## 卡片与交互

统一流程卡片沿用现有任务卡片的视觉和打开详情行为，并补充紧凑的流程摘要：

- 视频名称（优先使用飞书配置的标题字段）；
- Taskboard 任务编号；
- 自动/手动执行模式；
- Auto-Cut 包别名；
- ZIP 验证状态、上传状态和失败原因；
- 当前阶段的更新时间。

真实任务列继续支持现有拖拽规则。上传相关列只用于查看和操作，不允许通过拖拽伪造上传状态：

- “上传队列”失败卡片提供重新上传；
- “上传中”显示处理中状态；
- “已上传”显示完成时间和目标摘要；
- 点击任意卡片打开同一任务详情，详情中继续提供选择 ZIP、加入队列、下载和删除等操作。

统一看板不在卡片上暴露本地路径、命令、模型参数或 Bridge 密钥。

## 数据合并与刷新

前端同时读取：

- 当前 `projectId` 的任务列表；
- 当前 `projectId` 的 artifact upload 列表。

通过任务 ID 和 artifact 关联关系在浏览器内计算阶段归属。以下事件触发增量刷新或重新计算：

- `task.created`、`task.updated`、`task.moved`；
- `artifact.created`、`artifact.deleted`；
- `artifact.upload.updated`。

加载期间显示按列的稳定骨架；上传列表失败时只在上传相关列显示错误，不清空已经加载的任务列。搜索和筛选同时作用于任务编号、视频名称、ZIP 文件名和 Auto-Cut 包别名。

## 兼容与迁移

- 现有 `completed_editing`、`upload_queue`、`uploading`、`uploaded` 的本地视图记忆仍可读取，但打开后统一落到流程看板；不删除任务或上传记录。
- 旧的独立视图组件和接口暂时保留，便于回滚和排查；首版不再在主工具栏重复展示四个上传视图入口。
- 页面刷新、切换 Base 或切换学科后，统一看板仍只使用当前选中学科的项目 ID。

## 错误与安全

- 缺少当前学科上下文时显示空状态，不请求其他项目的数据；
- 上传目标未配置、ZIP 未验证或任务未达到可上传状态时，显示后端安全错误码对应的用户提示；
- 不因界面刷新而重复创建任务、重复入队或重复上传；所有写操作继续走现有幂等接口；
- 统一看板不改变 Bridge/Taskboard 的 loopback 绑定和自动执行授权边界。

## 测试与验收

实现时至少增加以下测试：

1. 阶段归属纯函数：上传中、排队/失败、已验证未上传、普通任务状态的优先级和单列归属；
2. 当前学科过滤：切换项目后不显示其他 Base 或子表任务及上传记录；
3. 上传事件刷新：上传状态变化后卡片从一个列移动到另一个列；
4. 旧视图记忆兼容：旧视图值打开统一流程看板且不丢失搜索/筛选；
5. 拖拽保护：上传相关列不接受状态拖拽，真实任务列保持原有行为；
6. 类型检查、前端构建、相关 Node 测试和本地服务健康检查。

手动验收顺序：先用已完成并已上传的历史任务确认统一看板显示，再创建一条新的自动处理测试任务，观察“待处理 → 排队中/处理中 → 已完成剪辑”，随后用现有手动上传操作验证“上传队列 → 上传中 → 已上传”。UI 调整不应改变自动处理的实际执行结果。

## 后续扩展（不在本次实现）

- 用户自定义流程阶段的新增、编辑、删除和排序；
- 按学科配置不同素材来源和字段映射；
- Auto-Cut 分支路由和学科代码识别；
- Base 总览统计视图。
